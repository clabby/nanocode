- Do not add code comments, doc comments, or comment headers.

- Do not add project Cargo features or `cfg(feature = ...)` branches. Use crate boundaries and native/WASM target gates.
- Follow [the crate layout](crates/README.md): active orchestration in `runtime/`, provider code in `backends/`, shared contracts in `core/`, and host adapters in `integrations/`. Keep each backend's API definitions and tools in its own provider-owned crates: `backends/<provider>/client` owns the provider wire protocol, authentication and transport without runtime, tool-host, Code Mode or durability dependencies, so it compiles alongside the runtime; `backends/claude/tools` owns independent Claude tool definitions and handlers without client or runtime dependencies; `backends/<provider>` owns the agent driver, tool assembly and durability and re-exports the client and tool paths.
- Keep runtime crates backend-generic. Code Mode owns only exec/wait contracts and cell orchestration. Keep generic tool selection and execution in runtime/tool-host, macro-free invocation contracts in core/tool-contracts, and MCP, remote transports and machine adapters in integrations/tool-runtime. Each backend owns its tool names, descriptions, schemas, formats and handlers, and supplies them to the host layer.
- Maintain one Rust crate workspace with reusable crates that compile individually for native and WASM targets. Keep language bindings, separately packaged WASM SDKs, managed services, and apps outside this repo. Do not add wasm-bindgen glue.
- Preserve agreed public APIs. Use upstream Claude/Codex prompts and tools; share Code Mode and CUA across both backends.
- Prioritize the Rust/WASM SDK. Enable Claude and Codex together, with in-place tool registration and dynamic remote execution through shared host contracts. Keep nanocode a thin public re-export surface; generic orchestration belongs in runtime/agent and backend construction belongs in each backend.
- Keep embedded Code Mode and on-disk durability as the native CLI defaults. An explicitly configured Code Mode host must replace the local evaluator without starting local machine tools. Keep inference, subagents and durability in the brain; execute remote Code Mode on the user's configured machine.
- Use the same remote Code Mode protocol whether the brain initiates a connection or accepts a runner connection, on loopback or across machines. Keep socket and storage adapters replaceable for WASM hosts such as Workers; in-memory storage is not persistent durability. Preserve cancellation and report uncertain remote outcomes without silently replaying dispatched work.
- Preserve authentic, version-pinned upstream provider system prompts and tool shapes, including names, descriptions, schemas and formats. Keep host, project and Code Mode additions separate. A provider version header is not prompt provenance.
- Codex API-key authentication defaults to store: true, so HTTPS calls after a session's first, or its first after reopening from storage, send only new input with `previous_response_id`, and a `previous_response_not_found` reply retries at once as a full replay. OpenAI keeps stored responses for 30 days in the organization that owns the key (Cloudflare's for AI Gateway Unified Billing) and treats store as false for Zero Data Retention organizations, which should set `.store(false)`. ChatGPT authentication keeps store: false, as upstream Codex always has for chatgpt.com/backend-api/codex (openai/codex ea01a5ffe2, 5775174ec2). Vercel and Cloudflare's provider-native OpenAI gateway keep store: true; OpenRouter and Cloudflare's unified Responses API, which replaces response IDs and rejects them as `previous_response_id`, stay stateless, as do Chat Completions gateways. On 2026-10-19 through AI Gateway continued Sol calls sent 2.1 KB instead of 37–45 KB but reached their first byte about 0.2 s later than full replays in an interleaved A/B, so prefer `.store(false)` where call latency matters more than request size.

- Local development keeps incremental compilation enabled, omits debug information and skips the post-link strip, which costs about 0.8 s per binary on macOS. .cargo/config.toml compiles workspace crates through scripts/rustc-parallel-frontend, which enables rustc's parallel front end with `-Zthreads=0`; dependencies compile unchanged, clippy keeps its own wrapper, and `RUSTC_WORKSPACE_WRAPPER=` disables it. Release builds use `lto = "off"`: cross-crate thin LTO cost about eleven times the CPU of an edit-to-install rebuild without measurable TUI runtime gains, and the per-crate ThinLTO that `lto = false` still runs cost 37% of an uncached release build (969 against 1,535 CPU-seconds) for 5-9% faster TUI rendering benchmarks; use the maxperf profile when LTO is wanted. Use the profiling profile for full symbols and the ci profile for disposable CI builds without incremental artifacts. Measure fresh-target builds separately from cached and edited rebuilds.
- .cargo/config.toml also routes rustc through scripts/buildcache, which shares compiled crates across target directories through ~/.cache/nanocode/build and needs no other tool. The shell script only dispatches: every call runs a helper that it compiles from scripts/buildcache.rs with the calling rustc into ~/.cache/nanocode/build/bin, in the background on first use while those calls run uncached. Clippy units are cached like other workspace units, keyed additionally by the clippy-driver digest, CARGO_PRIMARY_PACKAGE and CLIPPY_* variables, which clippy-driver reads without recording them as env-deps; their lint diagnostics replay from the cached stderr. A registry unit is keyed by rustc version, its arguments without target-directory paths, the identities of its `--extern` inputs and the CARGO_* environment, and its entry is immutable. A workspace unit is keyed the same way plus the workspace root and wrapper contents; its single entry is replaced on each store and is restored only when its `--extern` identities, package and workspace Cargo.toml and every dep-info source digest still match, so a fresh target directory of an unchanged tree in the same checkout restores instead of compiling, while other checkouts miss because cargo's `-C metadata` hashes differ there. An output's identity is memoized next to it: the unit key for registry outputs and the rmeta SHA-256 for workspace outputs, written when rustc reports the artifact and before the notification reaches cargo, so pipelined dependents never hash or race it; restores write the recorded identities before replaying stderr. Every restore is a copy-on-write clone checked against the env-deps rustc recorded, and units whose dep-info reaches outside the registry, the workspace or the content-addressed OUT_DIR copies are not stored. Build-script OUT_DIR and native search paths are swapped for content-addressed copies in which cc-rs object names derived from the absolute OUT_DIR, and the matching archive members, are renamed to the names a relative OUT_DIR would produce, so -sys crates key identically in every target directory. C objects compiled by build scripts are cached in direct mode: keyed by compiler version, cwd, arguments, environment and source digest with OUT_DIR mapped out, checked against the digests of every header in the compiler's `-MD` dependency file, and compiled with `-ffile-prefix-map`; sources or headers that use `__DATE__`, `__TIME__` or `__TIMESTAMP__` are not cached. SHA-256 uses the ARMv8 SHA2 instructions when the CPU has them. A target directory filled from the cache has no incremental state, so the first edit there recompiles the affected crates in full. Use `RUSTC_WRAPPER=` for cold-build measurements; deleting ~/.cache/nanocode/build only makes cargo rebuild the crates that referenced it.

- [Principles for fast Tokio applications](https://dial9-rs.github.io/blog/principles-for-fast-tokio-applications/)
- Write lock-free code: no Mutex, RwLock or Condvar from std, Tokio, futures or parking_lot anywhere in the workspace. Use the nanocode-sync primitives: own mutable state in one task and talk to it over channels or an Actor, publish shared state as an Atom or ArcSwap value changed copy-on-write with side effects performed after the change commits, use Slot, Signal, atomics and OnceLock for take-once values and flags, Ordered to publish effects in commit order, and Sequencer or Owned only where a protocol requires one caller at a time across awaits.
- Keep blocking native storage work behind an owning worker and asynchronous message/response channels. Batch complete transactions there, including tail replay, index refresh, serialization and disk sync; native journals take no file locks. Async SDK construction and shutdown must await their completion without running filesystem work or joining worker threads on Tokio workers. Preserve synchronous compatibility entry points and durable acknowledgements.
- Route subagent journal writes through the per-root journal writer and acknowledge each request only after its store save completes. Keep subagent message, residency and journal serialization per root so a slow or fenced store for one root cannot stall another.
