- Follow [the crate layout](crates/README.md): active orchestration in `runtime/`, provider code in `backends/`, shared contracts in `core/`, and host adapters in `integrations/`. Keep each backend's API definitions and tools in its own provider-owned crates: `backends/<provider>/client` owns the provider wire protocol, authentication and transport without runtime, tool-host, Code Mode or durability dependencies, so it compiles alongside the runtime; `backends/claude/tools` owns independent Claude tool definitions and handlers without client or runtime dependencies; `backends/<provider>` owns the agent driver, tool assembly and durability and re-exports the client and tool paths.

Keep generic tool selection and execution in runtime/tool-host, macro-free invocation contracts in core/tool-contracts, and MCP, remote transports and machine adapters in integrations/tool-runtime. Each backend owns its tool names, descriptions, schemas, formats and handlers, and supplies them to the host layer.
- Maintain one Rust crate workspace with reusable crates that compile individually for native and WASM targets. Keep language bindings, separately packaged WASM SDKs, managed services, and apps outside this repo. Do not add wasm-bindgen glue.
- Preserve agreed public APIs. Use upstream Claude/Codex prompts and tools; share Code Mode and CUA across both backends.

Keep nanocode a thin public re-export surface; generic orchestration belongs in runtime/agent and backend construction belongs in each backend.
- Keep embedded Code Mode and on-disk durability as the native CLI defaults. An explicitly configured Code Mode host must replace the local evaluator without starting local machine tools. Keep inference, subagents and durability in the brain; execute remote Code Mode on the user's configured machine.
- Use the same remote Code Mode protocol whether the brain initiates a connection or accepts a runner connection, on loopback or across machines. Keep socket and storage adapters replaceable for WASM hosts such as Workers; in-memory storage is not persistent durability. Preserve cancellation and report uncertain remote outcomes without silently replaying dispatched work.
- `nanocode_code_mode::remote::RemoteClient` owns the brain side of the remote Code Mode protocol on every target: pending replies, brain and hand callbacks, detached cells and their turn generations, cancellation, operation deadlines and unknown outcomes after a disconnect. `RemoteClient::new` runs it over any `RemoteLink`, which only sends and receives frame batches and closes the connection, and returns a driver future the host spawns. `SocketTransport` in integrations/tool-runtime is the native WebSocket link with dialing, accepting, heartbeats, liveness and close frames; WASM hosts implement `RemoteLink` over their own sockets. Frames that start or settle work are `RemoteDelivery::Durable`, so a host can make its state durable before sending a batch that contains one; relayed hand calls and their results are `Immediate`. `RemoteLink::changed` runs after each received batch and finished callback, `RemoteActivity::busy` reports running callbacks and detached cells for host idle checks, and `RemoteActivity::is_alive` reports whether its client still exists.
- integrations/process stops a command's process group with SIGSTOP before it sends SIGKILL. macOS delivers a group signal to one member at a time, so with SIGKILL alone a cancelled shell could see its killed child exit and run its next command, such as a redirect that creates a file, before its own signal arrived: `/bin/zsh -lc` scripts killed 2 ms after they started did so in up to 18 of 400 rounds per run on a loaded laptop on 2026-10-19, and in none of 2,800 rounds with SIGSTOP first.
- Brains without a local evaluator install `CodeModeExecutors` as their Code Mode host, call `CodeModeExecutors::select_prompt_hand` for each prompt, which selects the hand that sent it, or the only attached hand when no default executor is set, and otherwise clears the session's selection, and add `PLACEMENT_INSTRUCTIONS` to the agent's instructions.
- Preserve authentic, version-pinned upstream provider system prompts and tool shapes, including names, descriptions, schemas and formats. Keep host, project and Code Mode additions separate. A provider version header is not prompt provenance.
- Codex defaults to store: false for every authentication mode and gateway, since every mode supports it, Zero Data Retention organizations treat store as false anyway, and OpenAI keeps stored responses for 30 days in the organization that owns the key (Cloudflare's for AI Gateway Unified Billing). WebSocket sessions continue responses from the connection's memory and HTTPS sessions replay the full history. `.store(true)` opts an API-key session into HTTPS continuation with `previous_response_id` where the endpoint can continue stored responses: the OpenAI API, Vercel and Cloudflare's provider-native OpenAI gateway. The builder rejects it for ChatGPT authentication, which upstream Codex never stores (openai/codex ea01a5ffe2, 5775174ec2), for OpenRouter and for Cloudflare's unified Responses API, which replaces response IDs and rejects them as `previous_response_id`, and Chat Completions gateways stay stateless. A `previous_response_not_found` reply retries at once as a full replay. Storage is the slow part, not continuation: in a 12-round interleaved A/B of a 37 KB Sol request through AI Gateway on 2026-10-19 (`output/store-responses/binding-probe/ab2.js`), median first bytes were 790 ms for a store: false full replay, 1009 ms for the same replay stored, 892 ms for a stored continuation and 846 ms for a store: false continuation of a stored response; continuation saves request bytes but no tokens, since cached input tokens matched.
- `OpenAiBuilder::host_transport` routes Codex Responses requests through a host `HostTransport`, so external crates can own authorization, such as MPP payment or a Worker's private egress, without a native reqwest client; native host transports are HTTPS-only and exclusive with `ChatGateway`. A host transport forwards requests the client already built: `HostConnectRequest::http_headers` and `socket_headers` carry the Responses and WebSocket handshake headers, with every gateway `headers()` entry on HTTPS and `Authorization: Bearer` only when `sends_bearer_token()` is true, `HostConnectionMetadata::from_response` and `HostError::rejected` read the upstream response, including Retry-After on a rejection, and `host::send_http` serves `HostTransport::http` through a `nanocode_http::layer::Sender`. `OpenAiAuth::gateway_managed()` accepts a host transport or an HTTP layer in place of an authenticating Cloudflare gateway, and `OpenAiAuth::host_managed_chatgpt()` is its ChatGPT-mode equivalent for transports that inject the subscription credential and account headers: it sends no token and reports a 401 that survives the host's own recovery as login required. Claude's `transport::SenderTransport` adapts the same `Sender` for `ClaudeClient::with_transport`, so a host that implements that one HTTP contract serves both backends.
- Each Codex agent opens its Responses WebSocket in the background when its driver starts, with a connect-only attempt that sends no request and is never retried; the first model call queues behind it on the connection actor and reuses the socket. A connect rejected with 426 activates the run's shared HTTPS fallback before it releases the connection actor, so queued calls start on HTTPS instead of opening another WebSocket; other connect failures leave the model call its full WebSocket retry budget.

- Hosts that drive durable turns by request ID classify a finished prompt with `AgentRuntime::durable_outcome`: a prompt that returned its message is `Completed`, and a failed one is classified from the configured store as `Completed` by replaying a turn the store records as completed to recover its final message, `Failed` or `Cancelled` once the store records it, `Waiting` while an execution policy asks to retry later, or `Interrupted` when the host must reopen the runtime from its checkpoint. `pending_turns` lists a session's pending request IDs, `durable_prompt` decodes a turn's stored input for resuming it, and `settle` reports a root quiescent with no pending turns after persisting its subagents, comparing activity revisions across the persist.
- A turn keeps running when its caller drops the turn or every handle to its agent: both backends finish and settle the running turn and the turns accepted behind it before the agent stops, so none stays pending until the session is reopened. `shutdown` instead stops the running turn, releases its claim and leaves it pending for the next owner to resume.
- `SessionEvents::start` merges a root's agent events and subagent updates into batches for an `EventSink` and returns a pump future the host spawns. It coalesces consecutive assistant and reasoning-summary deltas of the same agent, request and item, holds a batch that ends in a delta until the caller's window since the previous delivery elapses or a drain is requested, and `drained` answers once everything received has been delivered, or with the sink's error after a delivery failed. Drain requests reach the pump over a channel, so it holds no lock.

- Third-party storage implements one host interface and leaves every durability rule to core/durability. `KeyValueStore` runs over a linearizable `KeyValue` (get, put_values, compare_and_swap and an optional list_keys). `SqlStore` runs over a SQLite `Sql` host whose `transaction(operation, statements)` executes the SDK's statements with text parameters atomically and returns each statement's rows; Durable Objects, D1, libSQL and sqlite-wasm need nothing else. SqlStore owns the `states`, `owners` and `records` tables, which are the nanocode Worker's layout and are created on first use, and every statement: acquisition increments the fence in SQL, a replacement inserts its records and head only while the owner, fence and expected revision match and reads the head back in the same transaction to report Fenced or Conflict, and commit_many sends a group in one transaction with independent outcomes. Counters are decimal text so JavaScript hosts keep u64 revisions, and the fence stops at SQLite's INTEGER maximum. It reports no concurrent handles, so SharedStore groups concurrent commits into commit_many.
- Local development keeps incremental compilation enabled, omits debug information and skips the post-link strip, which costs about 0.8 s per binary on macOS. .cargo/config.toml compiles workspace crates through scripts/rustc-parallel-frontend, which enables rustc's parallel front end with `-Zthreads=0`; dependencies compile unchanged, clippy keeps its own wrapper, and `RUSTC_WORKSPACE_WRAPPER=` disables it. Release builds use `lto = "off"`: cross-crate thin LTO cost about eleven times the CPU of an edit-to-install rebuild without measurable TUI runtime gains, and the per-crate ThinLTO that `lto = false` still runs cost 37% of an uncached release build (969 against 1,535 CPU-seconds) for 5-9% faster TUI rendering benchmarks; use the maxperf profile when LTO is wanted. Use the profiling profile for full symbols and the ci profile for disposable CI builds without incremental artifacts. Measure fresh-target builds separately from cached and edited rebuilds.
- .cargo/config.toml also routes rustc through scripts/buildcache, which shares compiled crates across target directories through ~/.cache/nanocode/build and needs no other tool. The shell script only dispatches: every call runs a helper that it compiles from scripts/buildcache.rs with the calling rustc into ~/.cache/nanocode/build/bin, in the background on first use while those calls run uncached. Clippy units are cached like other workspace units, keyed additionally by the clippy-driver digest, CARGO_PRIMARY_PACKAGE and CLIPPY_* variables, which clippy-driver reads without recording them as env-deps; their lint diagnostics replay from the cached stderr. A registry unit is keyed by rustc version, its arguments without target-directory paths, the identities of its `--extern` inputs and the CARGO_* environment, and its entry is immutable. A workspace unit is keyed the same way plus the workspace root and wrapper contents; its single entry is replaced on each store and is restored only when its `--extern` identities, package and workspace Cargo.toml and every dep-info source digest still match, so a fresh target directory of an unchanged tree in the same checkout restores instead of compiling, while other checkouts miss because cargo's `-C metadata` hashes differ there. An output's identity is memoized next to it: the unit key for registry outputs and the rmeta SHA-256 for workspace outputs, written when rustc reports the artifact and before the notification reaches cargo, so pipelined dependents never hash or race it; restores write the recorded identities before replaying stderr. Every restore is a copy-on-write clone checked against the env-deps rustc recorded, and units whose dep-info reaches outside the registry, the workspace or the content-addressed OUT_DIR copies are not stored. Build-script OUT_DIR and native search paths are swapped for content-addressed copies in which cc-rs object names derived from the absolute OUT_DIR, and the matching archive members, are renamed to the names a relative OUT_DIR would produce, so -sys crates key identically in every target directory. C objects compiled by build scripts are cached in direct mode: keyed by compiler version, cwd, arguments, environment and source digest with OUT_DIR mapped out, checked against the digests of every header in the compiler's `-MD` dependency file, and compiled with `-ffile-prefix-map`; sources or headers that use `__DATE__`, `__TIME__` or `__TIMESTAMP__` are not cached. SHA-256 uses the ARMv8 SHA2 instructions when the CPU has them. A target directory filled from the cache has no incremental state, so the first edit there recompiles the affected crates in full. Use `RUSTC_WRAPPER=` for cold-build measurements; deleting ~/.cache/nanocode/build only makes cargo rebuild the crates that referenced it.

- [Principles for fast Tokio applications](https://dial9-rs.github.io/blog/principles-for-fast-tokio-applications/)
- Write lock-free code: no Mutex, RwLock or Condvar from std, Tokio, futures or parking_lot anywhere in the workspace. Use the nanocode-sync primitives: own mutable state in one task and talk to it over channels or an Actor, publish shared state as an Atom or ArcSwap value changed copy-on-write with side effects performed after the change commits, use Slot, Signal, atomics and OnceLock for take-once values and flags, Ordered to publish effects in commit order, and Sequencer or Owned only where a protocol requires one caller at a time across awaits.

Batch complete transactions there, including tail replay, index refresh, serialization and disk sync; native journals take no file locks. Async SDK construction and shutdown must await their completion without running filesystem work or joining worker threads on Tokio workers. Preserve synchronous compatibility entry points and durable acknowledgements.
