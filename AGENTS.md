- Do not add project Cargo features or `cfg(feature = ...)` branches. Use crate boundaries and native/WASM target gates.
- Follow [the crate layout](crates/README.md): active orchestration in `runtime/`, provider code in `backends/`, shared contracts in `core/`, and host adapters in `integrations/`. Keep each backend's API definitions and tools in its own provider-owned crates: `backends/<provider>/client` owns the provider wire protocol, authentication and transport without runtime, tool-host, Code Mode or durability dependencies, so it compiles alongside the runtime; `backends/claude/tools` owns independent Claude tool definitions and handlers without client or runtime dependencies; `backends/<provider>` owns the agent driver, tool assembly and durability and re-exports the client and tool paths.
- Keep runtime crates backend-generic. Code Mode owns only exec/wait contracts and cell orchestration. Keep generic tool selection and execution in runtime/tool-host, macro-free invocation contracts in core/tool-contracts, and MCP, remote transports and machine adapters in integrations/tool-runtime. Each backend owns its tool names, descriptions, schemas, formats and handlers, and supplies them to the host layer.
- `FunctionTool` in runtime/tool-host is the adapter for tools a host declares at run time, such as a JavaScript host's: each has a name, description and JSON Schema parameters, and its calls run through an `Arc<dyn FunctionHandler>` whose async `call` receives the tool name, the decoded JSON arguments and the `ToolContext`. An `Ok` value becomes the JSON tool output and structured result and an `Err` text a tool error; parallel calls stay off unless `parallel_tool_calls(true)`. Register it with `ToolsBuilder::tool` on either backend and target: it is offered directly and inside Code Mode, and the backends keep its receipt like any tool's, so an interrupted call reports an unknown outcome instead of running again. gakonst/nanocode-wasm registers its hosts' tools this way.

- `nanocode_code_mode::remote::RemoteClient` owns the brain side of the remote Code Mode protocol on every target: pending replies, brain and hand callbacks, detached cells and their turn generations, cancellation, operation deadlines and unknown outcomes after a disconnect. `RemoteClient::new` runs it over any `RemoteLink`, which only sends and receives frame batches and closes the connection, and returns a driver future the host spawns. `SocketTransport` in integrations/tool-runtime is the native WebSocket link with dialing, accepting, heartbeats, liveness and close frames; WASM hosts implement `RemoteLink` over their own sockets. Frames that start or settle work are `RemoteDelivery::Durable`, so a host can make its state durable before sending a batch that contains one; relayed hand calls and their results are `Immediate`. `RemoteFrame::dispatches` marks the requests that start or continue work on the peer (Execute, Wait and Call), so a host can refuse to send them, for example once a turn's cancellation is requested, without decoding frames itself. `RemoteCatalog::decode` reads the catalog a hand or runner publishes as its first frame, with its tool definitions and advertised name, and rejects any other first frame with `NO_CATALOG`; the native `SocketTransport` and WASM hosts use it alike, so a host that stores the catalog across hibernation keeps it as opaque text. `RemoteLink::changed` runs after each received batch and finished callback, `RemoteActivity::busy` reports running callbacks and detached cells for host idle checks, and `RemoteActivity::is_alive` reports whether its client still exists. A link that wrote none of a batch, such as a host refusing it for a revoked hand or a cancelled turn, fails `send` with `CodeModeHostError::unsent`; when the connection ends, operations whose request no link accepted, or a link refused that way, report that they were not dispatched, and only requests a link may have written report unknown outcomes. `RemoteLink::max_frame_bytes` is the largest frame both ends accept: `SocketTransport` and the WASM package's link take the smaller of their own policy and the `max_frame_bytes` a hand or runner publishes in its catalog, and every request carries it, so the hand learns the brain's limit. No side writes a larger frame: the brain fails an oversized request as not dispatched and replaces an oversized callback result with the limit error; a hand replaces the inputs and outputs of an oversized result's nested calls, and then its output, with the limit error while keeping its cell, sends oversized nested-call updates without their payloads and fails an oversized cross-hand call without dispatching it. Before this, one 1.5 MB `text()` or cross-hand `Write` on a Worker hand closed the connection and failed every pending call with an unknown outcome. Execute and Wait deadlines add the operation's requested `yield_time_ms` to the operation timeout, because a model-chosen yield longer than the host's timeout otherwise expired the deadline and cancelled the turn's cells; Call deadlines are the timeout alone. Each client starts its request IDs at a random offset below 2^52, so when a host hands a connection to a new client, as the Worker does for a runtime reopened after a failure, a late reply to the previous client's request cannot reach the new client's request with the same ID. A client knows only the cells its own requests started: when a host hands a live connection to a new client, as the Worker does after a forced Durable Object restart while a hand stays attached, the hand keeps running the previous client's cells, and the new client drops their `DetachedUpdate` and `DetachedComplete` frames, so their completion notices are lost, answers their brain callbacks as unavailable, never answers a callback the previous client was still running, which then waits for the hand's callback deadline (`nanocode hand` sets none), and sends turn controls such as CancelTurn only to hands it has used itself; a Wait on such a cell's ID still reaches the hand through the session's placement. Reporting or cancelling those cells needs the hand to learn that its client changed, or durable records of each session's hands and cells.
- integrations/process stops a command's process group with SIGSTOP before it sends SIGKILL. macOS delivers a group signal to one member at a time, so with SIGKILL alone a cancelled shell could see its killed child exit and run its next command, such as a redirect that creates a file, before its own signal arrived: `/bin/zsh -lc` scripts killed 2 ms after they started did so in up to 18 of 400 rounds per run on a loaded laptop on 2026-10-19, and in none of 2,800 rounds with SIGSTOP first.
- Brains without a local evaluator install `CodeModeExecutors` as their Code Mode host, call `CodeModeExecutors::select_prompt_hand` for each prompt, which selects the hand that sent it, or the only attached hand when no default executor is set, and otherwise clears the session's selection, and add `PLACEMENT_INSTRUCTIONS` to the agent's instructions.
- A session's Code Mode placement is its own selection, then its root session's (linked through `Tools::for_session`), then the replacement default, then this machine. A selected executor that is not connected fails the cell without dispatching anything and never falls back to another machine, and executor failures, including unknown outcomes after a dropped connection, are failed cell outputs rather than host errors. Wait goes to the most recent placement with a running cell from that session, turn and cancellation controls reach every executor the session used, and model-visible tool definitions do not change with placement. Hands are chosen per call: a nested call whose arguments include `hand` (freeform tools take `{ input, hand }`) runs on that hand through `HandCalls` unless it names the machine running the script, skips the local admission gate, passes the target's and fails on its own, so `Promise.all` across hands settles each call separately.
- Code Mode nested calls on one tool runtime pass an admission gate, as Codex's parallel_execution lock gates its tool calls: tools a backend's `CodeModeToolPolicy` marks exclusive (Claude Write and Edit, Codex apply_patch) wait for running calls and block new ones, and every other call shares the gate. A shared call gives up its admission when its cell yields to the model (`CodeModeToolset::cell_observed`), as a Codex exec_command releases parallel_execution at its yield time, because an Edit had waited 272 s and 394 s behind shell commands whose cells had yielded; exclusive calls keep theirs until they finish.
- Remote Code Mode sockets derive liveness from `SocketPolicy.request_timeout`: each side pings every half of it and closes only when a ping sent after the last inbound message stays unanswered for another half, after draining buffered traffic, so a stalled local scheduler cannot fault a live peer and a frozen peer is detected within request_timeout of its last traffic. Pending operations then report unknown outcomes; operation deadlines never close the connection. Pool-managed hand sockets and `nanocode hand` use `SocketPolicy::runner()`: tungstenite's default 64 MiB message limit and twice the attachment heartbeat interval, so both sides ping every 20 s like attachment heartbeats, and calls have no deadline unless the caller passes `call_timeout_ms`.
- `RunnerPool` accepts tool runners and remote Code Mode executors on the same connect and listen paths, and the first frame decides: a catalog with `definitions` registers an executor in the pool's `CodeModeExecutors`, anything else continues as an attachment runner on the open socket. `RunnerPool::keep_connected` redials startup runners with the attachment backoff, connects through the runners tool and /runner fail fast, an executor reconnecting with the same advertised runtime id replaces its registration, and a different live executor with that name is rejected with a policy close. Disconnect permanently revokes a registration and resolves its pending calls, sent ones as uncertain and unsent ones as unavailable, before awaiting socket teardown; pool shutdown closes executors without revocation so they reconnect when the brain returns. `remote::Hand` is the hand side: `Hand::connect` dials and reconnects until the brain revokes it or closes it with `HAND_REPLACED` (`HandEvent::Replaced`), which the Worker sends to the older of two hand processes attaching under one name so they do not displace each other in a loop, `Hand::listen` accepts brains on a loopback address, its name defaults to `Hand::machine_name()`, and its directory is only where cells start.

- Codex defaults to store: false for every authentication mode and gateway, since every mode supports it, Zero Data Retention organizations treat store as false anyway, and OpenAI keeps stored responses for 30 days in the organization that owns the key (Cloudflare's for AI Gateway Unified Billing). WebSocket sessions continue responses from the connection's memory and HTTPS sessions replay the full history. `.store(true)` opts an API-key session into HTTPS continuation with `previous_response_id` where the endpoint can continue stored responses: the OpenAI API, Vercel and Cloudflare's provider-native OpenAI gateway. The builder rejects it for ChatGPT authentication, which upstream Codex never stores (openai/codex ea01a5ffe2, 5775174ec2), for OpenRouter and for Cloudflare's unified Responses API, which replaces response IDs and rejects them as `previous_response_id`, and Chat Completions gateways stay stateless. A `previous_response_not_found` reply retries at once as a full replay. Storage is the slow part, not continuation: in a 12-round interleaved A/B of a 37 KB Sol request through AI Gateway on 2026-10-19 (`output/store-responses/binding-probe/ab2.js`), median first bytes were 790 ms for a store: false full replay, 1009 ms for the same replay stored, 892 ms for a stored continuation and 846 ms for a store: false continuation of a stored response; continuation saves request bytes but no tokens, since cached input tokens matched.

- Hosts that drive durable turns by request ID classify a finished prompt with `AgentRuntime::durable_outcome`: a prompt that returned its message is `Completed`, and a failed one is classified from the configured store as `Completed` by replaying a turn the store records as completed to recover its final message, `Failed` or `Cancelled` once the store records it, `Waiting` while an execution policy asks to retry later, or `Interrupted` when the host must reopen the runtime from its checkpoint. `pending_turns` lists a session's pending request IDs, `durable_prompt` decodes a turn's stored input for resuming it, and `settle` reports a root quiescent with no pending turns after persisting its subagents, comparing activity revisions across the persist. A host that queues prompts before a runtime opens checks each with `admit_prompt`, which returns a `PromptRejection` for a request ID with the `COMPLETION_REQUEST_PREFIX` the subagent runtime uses for its own continuation turns and for a requested harness that differs from the session's recorded one.
- A turn keeps running when its caller drops the turn, the prompt call that admitted it or every handle to its agent: both backends finish and settle the running turn and the turns accepted behind it before the agent stops, so none stays pending until the session is reopened. `shutdown` instead stops the running turn, releases its claim and leaves it pending for the next owner to resume. It leaves the turns queued behind it that carry a request ID pending the same way, so the next owner resumes each of them once in accepted order, and cancels queued turns without a request ID and compactions. A subagent whose turn `shutdown` stops stays running in its root's subagent journal with its in-flight evidence, so the next owner resumes it from its latest checkpoint as after a crash instead of reporting it interrupted to its parent.
- A turn left `TurnStatus::Pending` by a retryable failure or a crash blocks different prompts with a Retry `OperationBlocked` error, and admission refuses a new operation while an unclaimed turn is pending without recording anything; a turn claimed by a live attempt or a queued admission does not block. Agents opened through AgentRuntime resume pending prompt turns in accepted order before the first new prompt, and a prompt call dropped while it resumes them hands the turns it has not resubmitted to the next one. Replaying one with `PromptRequest::new(agent.decode_durable_prompt(turn.input)?).request_id(turn.id)` reports interrupted tool calls as unknown outcomes instead of repeating them, and `.cancel_on_admission()` records it Cancelled without a model request. When two hosts open one session, the latest opener fences the other, whose turns stop without settling, and resumes the pending turns.
- AgentRuntime serializes open, open_loaded, open_session and durable resume per session id, and an open that finds a live agent returns it with a new `Agent::subscribe` stream instead of fencing it. An adopted agent whose prompt is refused before its turn started with AgentStopped, TurnStopped or a Reopen disposition, or whose store shows another owner, rebuilds its backend through `AgentOwner::reopen` under every existing handle, resumes the pending turns in accepted order and retries once; a prompt call dropped while it heals lets the next one heal, and explicit shutdown or disconnect turns healing off.
- `SessionEvents::start` merges a root's agent events and subagent updates into batches for an `EventSink` and returns a pump future the host spawns. It coalesces consecutive assistant and reasoning-summary deltas of the same agent, request and item, holds a batch that ends in a delta until the caller's window since the previous delivery elapses or a drain is requested, and `drained` answers once everything received has been delivered, or with the sink's error after a delivery failed. Drain requests reach the pump over a channel, so it holds no lock. `SessionEvent` implements `Serialize` as the hosts' wire format: `{"source":"agent","event","sdk_timing"}` for agent events and `{"source":"subagent","root_session_id","detach","update"}` with a typed `update` for subagent updates.
- `SessionLog` and `TurnInbox` in runtime/agent host a session's turns and events for any host that runs SQL, like `SqlStore`: the SDK owns the schema and every statement and the host only runs `Sql::transaction`. `SessionLog` owns the `turns` table and the `events` table in the nanocode Worker's layout (`seq` as the plain integer primary key, a scope column for several logs in one database). `submit` records a queued turn and its `queued` event in one transaction, returns the existing turn for the same prompt and hand, which it compares by a BLAKE3 payload digest so finished turns keep no prompt, and reports a conflict otherwise; `turn`, `pending` and `page`/`turn_page` read status, unfinished turns in admission order and events by cursor or within a turn's own `first_seq`..`last_seq` range, without opening a session; `cancel` finishes a queued turn at once and marks a running one; `interrupted` notes a recovery on a running turn; `import` adopts turns a host recorded before. A turn's result is its `result` event at `last_seq`, and `TurnRecord::report` returns it with the request ID and status. Pending lookups scan the scope's turn rows instead of keeping an index: on Durable Objects a row read costs a thousandth of a written row, and an index entry would add two writes to every turn. `TurnInbox::open` loads or creates the session and starts `SessionEvents` with a sink that encodes each event, attributes it to its request (Codex turn IDs map to the request through the `input.accepted` event that names both), appends each batch in one transaction and hands the logged events to `InboxHost::publish`. `drive` runs one root turn at a time: SDK operations still pending, in accepted order, through `durable_prompt`, then the oldest queued turn, which the SDK accepts only when it starts so `InboxHost::place` can select that turn's hand, and it records the outcome from `durable_outcome` or returns `Waiting` or `Interrupted` for the host to retry or reopen. `TurnInbox::cancel` also cancels the live turn or makes the next drive cancel it on admission, `settle` reports quiescence, and `InboxHost::finishing` adds host fields such as timings to a result. `SessionLog::retry` records why an unfinished turn waits on a host it cannot reach: the error, the host's kind for it, an attempt count kept in SQL and the next retry time sit on the turn row, its report shows them as `error`, `kind`, `attempts` and `retry_at` until the turn starts or finishes, and a `retrying` event is appended only when the error or kind changes, so retries add no events. Hosts end a turn they cannot run with `finish`, and `drive` cancels on admission, instead of running, an SDK-pending turn whose log record failed or was cancelled meanwhile. The `retry` column came after the first release, so each `SessionLog` checks `pragma_table_info('turns')` once, in its own transaction before its first operation, and adds the column when it is missing.

- Third-party storage implements one host interface and leaves every durability rule to core/durability. `KeyValueStore` runs over a linearizable `KeyValue` (get, put_values, compare_and_swap and an optional list_keys). `SqlStore` runs over a SQLite `Sql` host whose `transaction(operation, statements)` executes the SDK's statements with text parameters atomically and returns each statement's rows; Durable Objects, D1, libSQL and sqlite-wasm need nothing else. SqlStore owns the `states`, `owners` and `records` tables, which are the nanocode Worker's layout and are created on first use, and every statement: acquisition increments the fence in SQL, a replacement inserts its records and head only while the owner, fence and expected revision match and reads the head back in the same transaction to report Fenced or Conflict, and commit_many sends a group in one transaction with independent outcomes. Counters are decimal text so JavaScript hosts keep u64 revisions, and the fence stops at SQLite's INTEGER maximum. It reports no concurrent handles, so SharedStore groups concurrent commits into commit_many.
- StateStore: `peek` is required, because SessionStore::load, resume, branching and child journals read through it without fencing, and `owner` reports the current owner token without fencing; its unsupported default makes AgentRuntime treat a live agent's ownership as unknown. `acquire_with` runs its owned, synchronous StoreUpdate once against the acquired state; updates only calculate, None acquires without changing the revision, and the default acquire-then-replace reports failures after acquisition as Backend errors. `acquire_with_companion` acquires a distinct companion with the primary: an equal companion is NotCommitted before any write, NotCommitted means neither state changed, any other error leaves both uncertain, and a batching adapter validates both fences and revisions first and acknowledges only once the whole batch is durable. `commit` checks the fence and revision like `replace`, replaces the payload, advances the revision once, inserts absent records and appends events atomically; conflicting record content or a seq overflow is NotCommitted before any write, the default rejects events with NotCommitted, and events take contiguous seqs after the state's last, from 1, never reused. `commit_many` returns one result per commit in order, each judged on its own fence and revision; a shared write acknowledges none before it is durable, and a failed group may leave any subset committed. `supports_events`, `supports_summaries` and `batches_companion_acquisition` stay fixed per adapter and wrappers forward them; `concurrent_handle` returns a handle only when operations stay correct concurrently, including on one state; `flush` is an ordered barrier. `list_records` returns every record key of a state, for repairs that must find records by content; it is unsupported by default, and SqlStore, KeyValueStore (over `list_keys`), JSONL, SQLite and Postgres implement it and SharedStore forwards it.
- StateReader never acquires, fences or changes a revision: `read_state`, `read_records` and `read_events` are strongly consistent per state, while `query_states` and `query_events` come from an index that may trail commits. A summary belongs to the revision that committed it; index updates are idempotent by (state_id, revision) and (state_id, seq), Remove keeps a tombstone that queries never return, and an asynchronous indexer persists the publication intent in the commit's transaction. `query_states` orders by (updated_at_ms, state_id) and `query_events` by (at_ms, state_id, seq), both descending, and `read_events` by seq between exclusive bounds; pages are live keyset pages, a zero limit returns an empty page, `usize::MAX` is valid and adapters impose no hidden caps. scope, parent, state_id and attributes match exactly, kinds match any listed kind, and text is an ASCII-case-insensitive literal substring of the title, preview or event texts.
- Payloads are BLAKE3-addressed: one inline `b3:` record under 16 KiB, otherwise content-defined `c:` chunks under a manifest keyed by its own hash. A manifest that would reach 16 KiB becomes a tree cut where a hash prefix is divisible by CHUNK_AVG / 64, so a save rewrites only the groups around its edits: on a 60-turn, 4 MB local Claude session manifest bytes fell from 2.39 MB to 1.55 MB. Keys without `b3:` are SHA-256 records from earlier builds that still load and verify, and `EncodedPayload::matches_key` treats a SHA-256 key of the same content as equal, so receipts and step inputs recorded before the change still match. Records are immutable and never deleted, so a session driver counts every record its loads read (the latest checkpoint at agent acquisition and `LoadPayload(s)`, through `EncodedPayload::load_noting` and `load_many_noting`) among its committed records, and the first save after a restore stages only chunks the load did not read: before, it resent every chunk of a re-encoded checkpoint, and in the Worker's `measure-store.mjs` on 2026-10-20 a Claude turn restored after 60 turns of 200 text deltas sent 172 statements and 2.29 MB over the WASM bridge, against 71 and 1.31 MB now and 70 and 1.24 MB for a warm turn, and took 43.0 ms instead of 48.3 ms.
- KeyValueStore keeps a state's head at `{prefix}state/{state_id}` and its content-addressed records at `{prefix}record/{state_id length}/{state_id}/{key}`, written before the head swap and never deleted, so a failed replace leaves only unreferenced records. Versions are `fence.revision.owner` strings the adapter chooses and hosts store and compare verbatim; a failed swap rereads the head to report Fenced or Conflict, and acquisition retries until it installs the next fence. compare_and_swap must be linearizable per key, so eventually consistent stores such as Cloudflare KV cannot back it.
- runtime/durability session drivers: SessionStore::session and resume and DurableSession::open, open_shared, open_shared_described and open_sibling acquire ownership and persist the record before returning, fencing earlier owners. prepare_session, prepare_resume and prepare_shared_described return a driver without writing, and its first command acquires once through acquire_with with the prepared record merged, which JSONL commits with one full disk sync, so use them only where construction consumes the driver at once. `acquire_agent_with_initial_checkpoint` commits the backend's initial checkpoint in that acquisition when the state has no record, checkpoint or operations and returns `InitialAcquisition::Existing` otherwise, and `seeded_child_journal` with `acquire_agent_with_initial_checkpoint_and_journal` folds the subagent tree acquisition into the same synced batch only when the store batches companion acquisition, never on WASM. NotCommitted acquisition failures may be retried; other failures poison the driver. Startup durability is bounded by full disk syncs, about 5 ms each with F_FULLFSYNC on APFS, so measure entries, syncs and latency when changing acquisition paths.
- `DurableOwner::commit_writes` applies one operation's `OwnerWrite` values in order with one commit and one revision; nothing commits when any write fails, and a BeginStep for an existing step returns its Interrupted or Replay outcome without writing (three commits per tool step took 5.9 ms instead of 18.6 ms). `DurableSession::stage` queues a `SessionWrite` onto the driver's next commit of any kind, including a live agent's owner commits. NotCommitted keeps it queued; any other error peeks the state: the payload at the expected revision means the commit landed, the previous revision is retried once with the same revision-conditional commit, and anything else poisons the driver. `append` commits staged writes at once, `commit_checkpoint` commits a standalone checkpoint with its write, and after either fails with NotCommitted flush with an empty append, because retrying the same write duplicates its events. `MetadataWrite` is a data-only compare-and-set that cannot change identity fields. `DurableOwner::abandon_stale_kinds` registers maintenance kinds, Codex standalone_compaction and Claude compact and session_end, that the driver cancels when unclaimed at the head of the pending queue; prompt turns are never abandoned.
- SharedStore checks `concurrent_handle` once: with handles each operation runs on its own handle and task and flush waits for every earlier operation; otherwise its actor sends mutations already queued for other states together through commit_many, and a read, acquisition, flush or second mutation of a grouped state ends the group (20 sessions committing 150 transitions each took 2.87 s instead of 17.5 s). Every driver commit carries the current summary when supports_summaries is true, `catalog::summarize` owns the StateSummary mapping, and summary preparation failures are NotCommitted. SessionStore::load renders a running turn from its continuation through `CheckpointFormat::hydrate_continuation` and names it in `StoredSession.in_progress`, `SessionReader` serves clients that hold only a StateReader, and `PagedWriter::sequence_cached` reuses only keys confirmed with `SequenceCache::committed` after their commit.
- store-jsonl takes no file locks: the single O_APPEND journal is the linearization point and keeps owner fencing across processes. A writer replays the tail, validates, appends its entries with one write and one full disk sync, then replays everything that landed before them and judges its own entries by the rule every reader applies: an acquire needs the next fence and a replacement the current owner and the next revision. Superseded entries are skipped by every reader and reported as Fenced or Conflict, or retried for acquisitions, and a fence, revision or owner fence beyond the next one is corruption. Multi-entry batches carry a batch id and count and apply all or nothing, commit_many appends independent unbatched lines, a writer after a torn tail starts with a newline, and readers never truncate. Every process sharing a journal must run this protocol; older binaries lock and truncate, so restart every writer after upgrading.
- The JSONL offset index (`nanocode-jsonl-index-v3`) is a disposable sidecar bound to the journal identity, committed offset and final indexed entry digest, and any mismatch rebuilds it once from the journal before appending. It is saved at flush, at orderly close and when the idle worker's saved index trails the journal by more bytes than the index file holds, since long-running windows otherwise left openers replaying up to 2.1 GB. Index copies use a 128 KiB buffer: copying and hashing an 11.8 MB sidecar took 37.9 ms with 8 KiB, 18.9 ms with 128 KiB and 18.8 ms with 1 MiB.
- `JsonlStore::compact` is explicit maintenance on the worker: it keeps every valid acquisition and revision, each state's current payload and every unique record, blanks older payloads so older binaries still read the result, and never prunes records by guessing reachability. It first appends a seal naming its pid; writers whose entries land after a seal poll from 1 ms, doubling to 100 ms (the 12.6 GB production snapshot took 31.4 s to compact, so the cap adds about 0.3%), and retry on the replacement, a dead sealer is unsealed by the next writer, and processes sharing a journal must share a pid namespace. The first acquire entry carries the `nanocode_journal` lineage, `<journal>.compact-<pid>` and `.index-<pid>` temporaries of exited processes are removed at open, and hard-linked journals are rejected.
- JsonlStore and SqliteStore are handles to one worker thread each with a one-command job channel: a dispatched mutation or flush runs to completion when its caller drops the future, only reads whose receiver is gone are skipped, dropping the handle never blocks and close awaits the worker. open and open_home validate synchronously before moving the journal or connection to the worker, while open_async, open_home_async and SQLite's from_connection_async do that on the worker. SQLite runs every IMMEDIATE transaction, including busy-timeout waits on another writer, on its worker: a 1 s external write hold left 2.7-4.9 ms maximum heartbeat gaps instead of 1.09 s.

The shell script only dispatches: every call runs a helper that it compiles from scripts/buildcache.rs with the calling rustc into ~/.cache/nanocode/build/bin, in the background on first use while those calls run uncached. - [Principles for fast Tokio applications](https://dial9-rs.github.io/blog/principles-for-fast-tokio-applications/)
- Write lock-free code: no Mutex, RwLock or Condvar from std, Tokio, futures or parking_lot anywhere in the workspace. Use the nanocode-sync primitives: own mutable state in one task and talk to it over channels or an Actor, publish shared state as an Atom or ArcSwap value changed copy-on-write with side effects performed after the change commits, use Slot, Signal, atomics and OnceLock for take-once values and flags, Ordered to publish effects in commit order, and Sequencer or Owned only where a protocol requires one caller at a time across awaits.
- nanocode-sync semantics: `Atom::update` clones the value, applies the change and retries the compare-and-swap, so a change may run more than once and must be free of side effects; `try_update` skips the store on None and `modify` on an error. `Signal` fires once for current and future waiters, `Slot` put and take swap atomically and never read in place: `is_empty` reads an occupancy count kept beside the value, because loading the value for the check made a concurrent take or put find it shared and drop it. `Ordered` delivers values in ticket order, so every ticket must be published exactly once. `Inbox` pushes by compare-and-swap and drains in push order. `SingleFlight` runs one future per concurrent burst, and a cancelled leader hands the flight to the next caller. `Sequencer` admits one `Turn` at a time in arrival order, and a cancelled `enter` passes an admission it already received on. `Owned` moves its value to the admitted caller as `Held` or `Leased` and back before the next turn. `Actor` runs jobs on its own task in call order and cancels a job whose caller drops its future; it needs a Tokio runtime natively or an installed platform host on WASM.

Batch complete transactions there, including tail replay, index refresh, serialization and disk sync; native journals take no file locks. Async SDK construction and shutdown must await their completion without running filesystem work or joining worker threads on Tokio workers. Preserve synchronous compatibility entry points and durable acknowledgements.

- The subagent journal `<root>:subagents` is format 4: its payload lists one content-addressed record per agent and the tail of a chain of 64-key message pages, and each agent state record references a profile record holding the descriptor, binding task, output schema and host context. The journal names every record by the key its store files it under, `EncodedPayload`'s: the BLAKE3 hash of the content below 16 KiB and of its manifest above. Builds from b22a444ae until 2026-10-19 named large records by their content hash, so a Codex child's checkpoint (38 KB, mostly its instructions and tool definitions) or a profile with a long task failed with `missing payload record` after a restart, every delegation tool of that root failed with it and the session never became quiescent. The child journal store resolves a key it cannot find by listing the journal's records once per journal (`StateStore::list_records`), assembling every manifest root and matching the BLAKE3 hash of its content (`EncodedPayload::manifests_by_content`), and `matches_key` accepts that content key, so journals those builds wrote load again; records written after a restore use manifest keys, and a child's old checkpoint key is replaced by its next checkpoint. A restored child that cannot resume, such as one whose checkpoint is still unreadable, settles as Failed with an error naming the cause and its in-flight calls, as a failed turn does, so the rest of the tree resumes and the root gets a completion turn for its direct children; a journal that cannot be restored at all keeps failing every delegation tool of its root with the restoration error, writes nothing over it, and counts as quiescent for `settle`, because nothing from it can run. Versions 1 to 3 still load and older binaries reject 4. Every ChildSession change goes through `Sessions::get_mut` or `insert`, which assign a fresh journal generation, so the writer reuses the record keys of unchanged agents; it updates its cache only after the store acknowledges a save. With 20 children making 50 Code Mode calls each the journal payload fell from 12 MB to 0.41 MB (output/durability-perf-20261018).
