JsonlStore is a handle to a dedicated worker thread that owns the journal, process lock, index and read cache. Each StateStore call sends one complete locked transaction as a job, so flock waits, tail replay, record reads, F_FULLFSYNC and index saves never run on an asynchronous runtime worker. The job channel holds one command: StateStore takes &mut self, so a handle has at most one live call, and the slot lets that caller queue its next command behind a cancelled predecessor that is still running; further sends wait for the slot instead of growing a queue. A dispatched mutation or flush always runs to completion even when its caller drops the future; only read jobs whose receiver is already gone are skipped. open and open_home stay synchronous and validate eagerly on the caller thread before moving the journal to its worker; open_async and open_home_async open, validate and save a reconstructed index on the worker. StateStore::flush saves the index behind earlier jobs without waiting for another process's lock. Dropping the handle never blocks: the worker drains dispatched jobs, saves the index the same way and exits. close awaits that exit. Measure heartbeat gaps on a current-thread runtime while another process holds the journal lock, together with cancellation, reopen and per-call overhead, when changing the worker; output/nonblocking-store-20261017 holds the consumer that measured a 1 s lock hold as about 1015 ms without heartbeats before and 15-35 ms maximum heartbeat gaps after, at 15-30 us added per uncontended read.

JsonlStore::compact is an explicit asynchronous SDK maintenance operation on the owning worker. It keeps all acquisition and revision entries, each state's current payload, and every unique immutable record. Older state payloads become empty strings, so the existing JSONL replay format remains readable by older binaries and historical checkpoints remain resolvable. It never prunes records by guessing reachability from an opaque payload. Compaction reports before_bytes, after_bytes and records_removed and skips publication if the rewrite would not shrink the journal. Schedule it in an idle maintenance window: it holds the process lock throughout the rewrite, so other writers wait, while Tokio workers remain free. Startup, close and ordinary flush do not initiate compaction.

A compacted journal's first acquire entry carries nanocode_journal, the original journal identity, which later compactions retain. Upgraded handles reopen a replacement only when this lineage matches, reset their offsets and caches, and acquire the current inode's lock before reading or writing. Unrelated replacements remain errors. Older already-open handles fail closed on an identity change; upgrade active writers before compacting their journal. Do not publish a stale sidecar for a replaced inode. Compaction preserves file permissions, synchronizes the replacement before atomic publication and the parent directory before acknowledging it, and rejects hard-linked journals because replacing one name would split their writers. Cancellation after dispatch does not abandon compaction.

The journal owns temporary filename prefixes formed from its filename followed by .compact- or .index-. Remove abandoned regular files in those namespaces while holding its process lock at open and before compaction. Do not remove unrelated temporary files. This bounds storage left by a killed compactor or index writer to work awaiting the next open.
