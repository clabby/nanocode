# Observability

- The local OTLP trace file is written by `file::TraceProcessor`, a native span processor that owns one worker thread. Ordinary `on_end` reserves a queue slot with an atomic compare-and-swap and sends the sampled span over a Tokio unbounded channel. It does not serialize, touch the filesystem, wait for the worker, block on a full queue or take an application mutex. A failed send after shutdown prints one diagnostic on the caller. Keep the ordinary span-end path free of I/O, blocking and application locks.
- The worker owns the file and resource. After each wake it snapshots the channel length and processes exactly that frontier, then writes the spans as one grouped OTLP JSON line through a buffered writer. Each batch is finite, so spans reach disk while producers keep running. Do not add separate batch-size caps or timers.
- Queue policy: the local processor keeps at most `OTEL_BSP_MAX_QUEUE_SIZE` sampled spans that have ended but are not yet written, counting spans in the channel and the batch being written. The default 2048 is the OpenTelemetry SDK environment specification default, and it matches `OTEL_BSP_MAX_QUEUE_SIZE_DEFAULT` in opentelemetry_sdk 0.32.1, which the HTTP `BatchSpanProcessor` uses. An unparsable value fails installation instead of falling back. When the queue is full, span end drops the span and increments an atomic counter. The worker prints each overflow count after its next write, and the next `force_flush` or shutdown returns an error with the dropped total. Producers are never blocked.
- Memory tradeoff: an unbounded queue keeps every span, but its memory grows with any backlog. With the synthetic probe in `output/nonblocking-otel-20261017` (11 attributes and one event per span), sustained overload at about 1M spans/s reached roughly 12 GB RSS in 2 s. With the bounded queue, the same overload peaked at 190–310 MB RSS, and the excess spans were reported as dropped. Paced load at about 5k spans/s wrote every span with no drops, near-baseline span-end latency and RSS of about 22–43 MB. Bursts above the queue size drop spans. Use sampling, filtering or a larger explicit `OTEL_BSP_MAX_QUEUE_SIZE` instead of blocking producers or adding an unbounded queue.
- `force_flush` returns after every accepted span that ended before the call is written. It reports the first write error or the overflow total since the previous acknowledgement. `shutdown_with_timeout` writes the bounded backlog, closes the file and acknowledges within the caller's timeout, or returns `Timeout` while the worker keeps writing. Spans that end after shutdown are reported once. Repeated flush or shutdown calls return `AlreadyShutdown`.
- Shutdown and flush are synchronous. Call them outside Tokio worker threads, as the CLI guard does.
- tracing-opentelemetry 0.33 and 0.34 have no `record_u64` in their span visitors, so `u64`, `usize` and `u32` span fields arrive as `Debug` strings. `typed::restore_integers` turns canonical non-negative decimal strings that fit `i64` back into integers on the trace writer thread and in the OTLP/HTTP exporter wrapper, so collectors can aggregate them. Leading zeros, signs and values above `i64::MAX` stay strings. Event attributes are left as recorded.

## Instrumentation

- tracing-opentelemetry ends a span at its last exit, not when it closes. Keep the span entered for the whole operation it measures, for example by instrumenting each stream poll, or the exported duration stops at the last poll. Record `duration_ns` when the measured work deliberately excludes queueing, as `tool.execute` does for admission.
- Parents are exported only when they end, so a running or interrupted turn leaves its children without an exported parent. Put `session.id` directly on agent-path spans: `model.call`, `tool.call`, `tool.execute`, `code_mode.cell`, `code_mode.cell_actor` and `code_mode.wait`. Cells and waits also carry the model's `tool.call_id`; nested calls use `<call_id>/code-<n>`.

## Analysis

- `scripts/otel.mjs` reads every `<home>/log/otel/*/traces.jsonl` and `metrics.jsonl`, remembers a byte offset per file and ingests only complete new lines into output/telemetry/telemetry.sqlite. Every command ingests first unless `--no-ingest` is given. A schema change rebuilds the cache.
- `spans.dur_ms` is the larger of the exported span length and the `duration_ns` attribute. `session_id` is the span's own `session.id`, else its nearest exported ancestor's (`session_from = 'parent'`), else the only session among the agent spans of its trace (`'trace'`). `ui = 1` marks terminal rendering spans, which keep only their own session. Other attributes are in the `attrs` JSON column; tool arguments and outputs are `events` rows with `kind` `tool.arguments` and `tool.output`.
- Every process exports `process.pid`, `process.executable.path` and `nanocode.executable.modified` (the executable's modification time in Unix microseconds) as resource attributes, so spans can be attributed to the build that produced them. `sources` keeps the first trace line's executable and build time; `--by build` groups by executable name and build time and `builds` lists builds with their processes, sessions and span counts. Older files without these attributes group as `- @ -`.
- Events with the `nc_metrics` target feed the metrics layer only; the trace layer drops them, because they fire inside `nc.frame` and were exported as span events on every frame (31 MB of 82 MB of frame span data in one 920 MB trace file).
- `nc.frame` records `frame.input_ms`, `frame.stream_ms` and `frame.resize_ms`, the time from the first input, stream event or resize it presents to the end of the frame, so per-event latency tails keep their session and process; the `frames` view exposes them with `cpu_ms`. The exported histograms keep the SDK default buckets (0, 5, 10, 25 ms and up).
- `nc.frame` records `thread.cpu_ns`, the main thread's CPU time during the frame (`CLOCK_THREAD_CPUTIME_ID`); the `frames` view exposes it as `cpu_ms`. A frame much longer than its CPU time waited: on a terminal write (see its `tui.terminal.write` child) or for a CPU while descheduled. In a synthetic run the three slowest frames (10.9-14.9 ms) used under 1 ms of CPU.
- Views are recreated on every open, so view changes need no cache rebuild; table changes bump `SCHEMA_VERSION`.
- Local telemetry has no retention: it grew about 3 GB an hour with five busy terminal windows. `prune --older-than <age>` deletes raw directories untouched for that long whose files are fully ingested and that no running process writes; `/reload` re-execs under the same pid, so only a live pid's newest directory counts as written. Spans of pruned files stay in the cache until a schema change rebuilds it. `--dry-run` lists what would go.
- `breakdown` sweeps each completed `agent.turn` and assigns every moment to the first active category: model calls (`model.call`, compaction, warmup), tools (`code_mode.cell`, `code_mode.wait`, Codex `tool.call`, the terminal's `nc.tool_call`), durable store writes, or other, which is the agent loop itself. Turns from builds before `code_mode.wait` existed, run without the terminal (subagents, `nc exec`), report their waits on yielded cells as other.
- `outliers` reports each span's process and `slow elsewhere`: how many other processes had a span of the same name over the same threshold overlapping it. Nonzero counts mark machine-wide stalls such as CPU contention; on 2026-10-18 the 93-161 ms idle frames all coincided with slow frames in one or two other nc processes, while the 193-382 ms diff-render frames coincided with none.
- Views: `tools` (nested tool executions with arguments, admission wait, hand and exit code), `cells` (exec cells and waits), `models`, `turns` and `frames`. `sessions` aggregates model, cell and tool time per session with lineage from `agent.turn`. The bundled SQLite provides `median` and `percentile`.
