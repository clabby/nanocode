# Codex upstream contracts

- Own Codex harness construction and reserved built-in tool names here. Tool handlers execute through core/process interfaces; native constructors remain compatibility defaults. Runtime assembly supplies host process executors.

- `client/` (`nanocode-backend-codex-client`) owns the Responses protocol, model configuration, authentication, transports and pinned base prompts; this crate re-exports it as `client` and keeps `OpenAi`/`OpenAiBuilder` so backend registration impls stay local.
- Preserve the exact prompt bytes and extraction provenance in `client/prompts/upstream.json`.
- Keep the immutable provider prefix on `ModelConfig::base_system_prompt`; place runtime identity and additional instructions in developer context. Preserve the public composed `system_prompt()` compatibility view and explicit system overrides.
- `upstream/tools.json` pins the reviewed standard tool sources, local artifacts, and selected upstream option profile. Re-audit affected contracts against that revision before updating artifact hashes.
- Run `python3 scripts/verify-codex-upstream.py` from the repository root to verify upstream hashes, prompt extraction, local artifact integrity, and exact patch grammar. `--offline` uses the ignored `output/codex-upstream-parity` cache. Without `--serialize`, this verifies artifacts without executing Rust tool serialization.
- Add `--serialize` to execute the pinned upstream standard tool builders in an ignored minimal consumer binary. `--consumer-dump PATH` compares its five serialized contracts against a public SDK consumer JSON dump containing `codex_standard`. The harness preserves upstream handler bodies, schema types and selected wire serializers while omitting unrelated host dependencies.
- Keep output schemas as host metadata, matching upstream omission from Responses tool serialization.
- Local `web.run`, `image_gen.imagegen`, attachment, and delegation functions are SDK extension contracts. Do not describe them as upstream provider server tool parity. Host routing and shared Code Mode can decorate or transform model-visible exposure independently of the pinned standard definitions.

## Responses gateways

- `client::transport::ResponsesGateway` routes the unchanged Codex Responses request (prompts, tools, input items, `client_metadata`) to third-party Responses endpoints on native and WASM. `OpenAiBuilder::responses_gateway` applies its base URL and vendor model prefix and selects HTTPS with no warmup. Where the gateway can continue a stored response it keeps store: true with incremental input, as for the OpenAI API (see Stored responses); OpenRouter and Cloudflare's unified API get stateless full replay with store: false, and `ResponsesGateway::supports_stored_responses` reports which. `.store(false)` after it selects full replay on any gateway. The Chat Completions `ChatGateway` is separate and native-only; a config may use only one of the two.
- Only Sol, Luna and Astra are served, because these gateways forward the OpenAI Responses shape to OpenAI models. Cloudflare's Codex integration documents the same limit: https://developers.cloudflare.com/ai-gateway/integrations/coding-agents/openai-codex/. Route GLM, Kimi and MiMo through `ChatGateway`.
- OpenRouter: `POST https://openrouter.ai/api/v1/responses`, `Authorization: Bearer` with the OpenRouter key, `openai/<model>` IDs. Optional `X-OpenRouter-Title` and `HTTP-Referer`. Routing goes in the body `provider` object. The endpoint is stateless and rejects `store: true` and `previous_response_id`. Docs: https://openrouter.ai/docs/api_reference/responses/overview, https://openrouter.ai/docs/api_reference/authentication, https://openrouter.ai/docs/guides/routing/provider-selection.
- Vercel AI Gateway: `POST https://ai-gateway.vercel.sh/v1/responses`, `Authorization: Bearer` with an AI Gateway API key or Vercel OIDC token, `openai/<model>` IDs. Routing goes in body `providerOptions.gateway`. Responses WebSocket mode at `wss://ai-gateway.vercel.sh/v1/responses` is documented for OpenAI models, one model per connection, with a 4 MiB frame limit, so WebSocket is opt-in only for Vercel. Its parameter reference lists `store` and `previous_response_id`, and its WebSocket guide continues store: false chains only on the same connection. Docs: https://vercel.com/docs/ai-gateway/sdks-and-apis/responses, https://vercel.com/docs/ai-gateway/sdks-and-apis/responses/websockets, https://vercel.com/docs/ai-gateway/authentication-and-byok, https://vercel.com/docs/ai-gateway/models-and-providers/provider-filtering-and-ordering.
- Cloudflare unified REST API (`ResponsesGateway::cloudflare`): `POST https://api.cloudflare.com/client/v4/accounts/{account}/ai/v1/responses`, `Authorization: Bearer` with a Cloudflare API token holding Workers AI Read, `openai/<model>` IDs, and optional `cf-aig-gateway-id`. It stores a store: true response but answers with an `id-<n>` ID in place of the provider's `resp_` ID and rejects that ID as `previous_response_id` with `invalid_prompt`, which the client treats as terminal, so the builder rejects store: true here. Docs: https://developers.cloudflare.com/ai-gateway/usage/rest-api/.
- Cloudflare provider-native OpenAI endpoint (`ResponsesGateway::cloudflare_gateway`): `POST https://gateway.ai.cloudflare.com/v1/{account}/{gateway}/openai/responses` with bare OpenAI model IDs. `Authorization` carries the OpenAI key or a Cloudflare token for Unified Billing. `cf-aig-authorization` authenticates an Authenticated Gateway, and `cf-aig-byok-alias` selects a stored key. `OpenAiAuth::gateway_managed()` omits `Authorization` so stored keys apply, and requires `gateway_token`. Cloudflare's WebSocket API is Realtime-only, so this path is HTTPS-only. Docs: https://developers.cloudflare.com/ai-gateway/usage/providers/openai/, https://developers.cloudflare.com/ai-gateway/configuration/authentication/, https://developers.cloudflare.com/ai-gateway/configuration/bring-your-own-keys/, https://developers.cloudflare.com/ai-gateway/usage/websockets-api/realtime-api/.
- `HostTransport::http` implementations must forward every `HostConnectRequest::headers()` entry. They must send `Authorization: Bearer` only when `sends_bearer_token()` is true. Native HTTPS applies the same headers.
- `OpenAiBuilder::host_transport` also routes native HTTPS Responses requests through the host, so external crates can own authorization such as MPP payment without a native reqwest client. Native host transports are HTTPS-only and exclusive with `ChatGateway`. `OpenAiAuth::gateway_managed()` accepts a host transport in place of an authenticating Cloudflare gateway. `OpenAiAuth::host_managed_chatgpt()` is the ChatGPT-mode equivalent for hosts whose transport injects the subscription credential and account headers, such as a Worker's private egress; it sends no token and reports a 401 that survives the host's own recovery as login required. A host transport forwards requests the client already built: `HostConnectRequest::http_headers` and `socket_headers` carry the Responses and WebSocket handshake headers, `HostConnectionMetadata::from_response` and `HostError::rejected` read the upstream response, and `host::send_http` serves `HostTransport::http` through a `nanocode_http::layer::Sender`.
- Gateway routing covers Responses inference. Built-in `web__run` and `image_gen__imagegen` adapters return an explicit unsupported result before authentication or network access under a Responses gateway; callers can register their own adapter tools. Preserve their advertised definitions. Codex inline compaction is supported only through the Cloudflare provider-native proxy; the translating gateways reject it before sending a request.

## Stored responses

API-key authentication defaults to store: true (`OpenAiAuthMode::supports_stored_responses`), so each HTTPS model call after the first sends only its new input items with `previous_response_id`, and a WebSocket session that falls back to HTTPS stays incremental after the fallback's own full replay. The OpenAI API keeps stored responses as application state for 30 days, in the organization that owns the key; through AI Gateway with Unified Billing that is Cloudflare's organization: https://developers.openai.com/api/docs/guides/your-data, https://developers.openai.com/api/docs/guides/conversation-state. Callers that must not retain conversations call `.store(false)` or `stateless_http()`, which select a full replay on every HTTPS call. Zero Data Retention organizations have store treated as false, so their continuations fail and retry as full replays; they should set store: false. A continued chain still bills every earlier input token, so storage reduces request bytes, not token cost.

ChatGPT authentication keeps store: false and the builder rejects store: true with it. Upstream Codex has never sent store: true to `chatgpt.com/backend-api/codex`: the commit that added that endpoint computed `store = prompt.store && auth.mode != AuthMode::ChatGPT` (openai/codex ea01a5ffe2, #1712), #3212 (5775174ec2) removed storage entirely, and the pinned revision sends `store: false`. Its WebSocket continues responses from the connection's memory instead. Chat Completions gateways and GLM, Kimi and MiMo stay stateless.

A 400 `previous_response_not_found` or `Invalid previous_response_id` answer to a continued request retries at once as a full replay without a backoff (`checkpoint_missing`). A replaced WebSocket, a repaired or compacted history, a model call resumed mid-turn from a checkpoint and the first call of a session reopened from storage also replay in full, since checkpoints do not keep the response ID; a resident session continues across turns. Measured through AI Gateway's OpenAI binding with gpt-6-luna on 2026-10-19 (`output/store-responses/binding-probe`): a store: true response continued with `previous_response_id`; a store: true full replay of items carrying IDs from a store: false response, and of client-assigned message IDs, succeeded; continuing a store: false response returned 400 `previous_response_not_found`; and store: false could continue a stored response.

The macOS timezone fast path accepts only an absolute /var/db/timezone/zoneinfo/ symlink whose name appears verbatim as a zone or link in the system tzdata.zi index. Keep TZ/TZFILE overrides, GMT/UTC parser cases and every unrecognized layout on iana-time-zone. Verify first-request and initial-checkpoint date/timezone parity and fallback behavior when changing it.

Check cached WebSocket liveness before selecting incremental input. Replacing a closed socket must replay full history without consuming a model retry or backoff. If a cached socket closes during dispatch, replace it within the attempt only when the pump proves the request was not dispatched; a new connection failure or uncertain delivery keeps ordinary retry reporting. HostConnection::is_closed defaults to false for compatibility; host adapters may return true only when they know their connection is closed. Keep connection events and reconnect statistics for routine idle replacement.

The Responses API documents a 60-minute connection lifetime and the `websocket_connection_limit_reached` rejection at https://developers.openai.com/api/docs/guides/websocket-mode. Renew a reused connection within the same attempt only when this exact top-level error is its first response event. Replay full context without `previous_response_id`, preserve raw API and reconnect telemetry, and consume no model retry or backoff. A fresh replacement failure, response progress before expiry, terminal quota errors, and unrelated API errors retain ordinary failure handling. The external consumer at `output/connection-renewal-20261018/expiry.py` exercised these seven cases across 56 processes; routine-expiry warnings fell to zero, with local fixture median second-turn latency falling from 969 ms to 12 ms.

Each agent opens its Responses WebSocket in the background when its driver starts, using a connect-only attempt that sends no request; the first model call waits on the connection lock and reuses that socket. A connect attempt is never retried. Its 426 rejection moves the session to HTTPS like a model call's does, because every attempt factory of a run shares the run's `TransportFallback`; other connect failures leave the model call its full WebSocket retry budget. The `generate: false` warmup is opt-in through `websocket_warmup(true)`. Measured on gpt-6-luna (output/cache-probe, nc exec and a TUI prompt typed 3 s after start, median of 4-6 runs): the warmup added 11.4K input tokens per session and moved first output from 2.05 s to 2.51 s in exec mode, while background connect gave 1.71 s in exec mode and 1.37 s in the TUI against 2.23 s with the warmup. A warmed first call reached first output about 0.2 s sooner than a preconnected one, which does not cover the warmup's own round trip and tokens.

Side questions send the reasoning effort and service tier of the thread's latest model request, recorded in `ModelPromptCache`, instead of the current defaults, because Responses prompt caching is partitioned by effort and a running turn keeps its own settings. On gpt-6-luna a side question after `set_thinking(High)` read no cached tokens in 5 of 5 runs; with the latest request's effort it read 24,448 of about 24,950 in 2 of 4 runs and the 11,136-token shared prefix in the others, as side questions without a settings change do (`output/fork-cache`, `side-effort` scenario). Forks and the thread's next turn keep the current selection.

Native HTTPS Responses requests with ChatGPT authentication and no gateway send zstd level 3 bodies with `Content-Encoding: zstd`, as upstream Codex does for the Codex backend when `enable_request_compression` (stable, on by default) is set. Compression runs on the blocking pool; host transport bodies are unchanged. A 354 KB full-history gpt-6-luna request went out as 78 KB and was answered from its content, and the next turn read 67,072 of 67,304 input tokens from cache (`output/transport/codex-probe`). On a 3.08 MB conversation body libzstd level 3 gave 4.26x in 10 ms and level 1 3.74x in 8 ms (`output/transport/zbench`). `responses.attempt` records `request.zstd_bytes`.

Responses WebSockets offer `permessage-deflate; client_no_context_takeover`, since upstream Codex enables permessage-deflate through its tungstenite fork. tungstenite 0.30 has no extension support and published crates cannot depend on git forks, so `transport/deflate.rs` handles it around tungstenite: `InflateStream` sits between TLS and the WebSocket codec, passes the handshake through and inflates server data messages that set RSV1 with one inflater that keeps the server's context, and `ResponsesSocket::send` deflates each outgoing text message on the blocking pool at level 2 (the level measured for Claude gzip) into a raw RSV1 frame with a fresh compressor, as the offer declines client context takeover. Servers that ignore the offer get plain frames. chatgpt.com accepted it with server context takeover: a 354 KB full-history request went out as 88 KB, an incremental one as 1.0 KB instead of 4.4 KB, and 58 server messages over three turns, one with an exec call, arrived as 148 KB instead of 466 KB (`output/transport/codex-probe`). `responses.attempt` records `request.deflate_bytes`.

Track each connection's age with the portable monotonic clock and replace it before dispatch once it reaches the documented 60-minute lifetime. Check again before encoding and sending in case the deadline passes during dispatch preparation. Use full replay on the replacement. The standalone WASM consumer at `output/connection-renewal-20261018/wasm-consumer` exercises just before, exactly at, and after the lifetime boundary, plus reactive expiry, with a virtual clock and a one-attempt policy; all cases complete without a model retry.

Managed native ChatGPT refreshes use the persistent auth-file .lock sidecar across processes, acquired off the async executor before reloading credentials and held through refresh and atomic persistence. Do not unlink the sidecar: replacing it would split ownership. Login persistence uses the same lock. Synchronous logout reports a busy lock rather than blocking an executor that may be driving the refresh. Recheck the stored authorization after the token response so a concurrent external credential change is not overwritten. Keep retry jitter tied to the request thread identity so independent sessions do not retry in lockstep, and preserve server-directed delays.

Async ChatGPT auth paths run auth-file reads, parsing, serialization and fsync on the blocking pool and never hold the in-memory state lock across disk I/O. The managed refresh runs as a spawned task that owns the in-process refresh mutex, so a cancelled caller cannot discard a rotated refresh token; the sidecar lock moves into the blocking save and is released only after the atomic rename. Managed auth state is an immutable `ArcSwap` value carrying the prebuilt snapshot and token expiry, so request-path snapshot reads take no lock and decode no JWT; only the serialized refresh task replaces it. The cross-process sidecar lock still serializes refresh-token use and is not lock-free. The synchronous loader, status and logout functions remain blocking calls for synchronous callers.
