Own the portable StateStore interface, owner and revision contracts, durability errors, content-addressed payload encoding and deterministic state transitions. Keep agent handles, session drivers, checkpoint catalogs and host storage implementations out. Keep the journal state independent of session metadata; parameterize only checkpoint serialization so the state model compiles once before agent lifecycle contracts. Preserve serialization and content-addressing formats; runtime/durability reexports these contracts for existing consumers. Native store futures remain Send and WASM store futures remain local. Native owner IDs use the same UUIDv7 generator without pulling in an executor; WASM uses the installed platform host for time and randomness.

StateStore::acquire_with invokes its owned, synchronous StoreUpdate once against the acquired state. None acquires ownership without changing the revision; StoreReplacement advances the revision once and preserves immutable records. Callbacks only calculate data and must not perform external work. Existing adapters inherit acquire followed by a fenced replace; failures after successful acquisition are Backend errors because ownership already changed. Adapters may combine the owner and replacement writes, but must commit both before acknowledging success and preserve fencing, revision checks and uncertain outcomes. Native callbacks are Send; WASM callbacks may be local.

StateStore::acquire_with_companion acquires a distinct companion state together with acquire_with on the primary state and reports the whole operation. An equal companion is rejected with NotCommitted before any write. NotCommitted means neither state's owner or revision changed; any other error leaves both states uncertain. The default acquires the companion and then the primary, so failures after the companion acquisition are Backend errors. Adapters may combine both acquisitions and the replacement into one synchronized batch, validating both fences and revisions first and acknowledging success only after the entire batch is durable. A failed or interrupted batch may leave a prefix committed. StateStore::batches_companion_acquisition reports this batching capability and defaults to false; its value stays fixed for an adapter. Wrappers return true only when they forward acquire_with_companion to an adapter that does, because callers then defer the companion acquisition into the primary one instead of overlapping it with other work.

StateStore::commit is the event-aware write. It checks the owner fence and revision exactly like replace (Fenced, Conflict), replaces the payload, advances the revision once, inserts records when absent and appends the events, and all of these commit or none do. A record with conflicting content, or an event batch whose last seq plus one would exceed u64::MAX, is NotCommitted before any write. NotCommitted means nothing changed; any other error leaves the outcome uncertain. The default rejects non-empty events with NotCommitted and otherwise delegates to replace, ignoring the summary, so adapters without an event log keep their behavior; acquire_with and its default stay replace-based and never publish summaries. Each state's events receive contiguous seq values after the state's last seq, starting at 1. Committed.first_event is the seq of the first event, or None without events. Seqs are never reused, including after a state is retracted, StoredEvent.revision is the committing revision, and events are immutable.

StateReader is the read-only side: read_state, read_records, read_events, query_states and query_events never acquire, fence or change a revision, and a client may hold only a reader. read_state, read_records and read_events are strongly consistent for one state and observe every acknowledged commit. query_states and query_events are served from an index that may trail commits, so they are eventually consistent across states and never promise visibility at the time a commit returns.

A summary belongs to the revision that committed it. Index updates are idempotent by (state_id, revision) for summaries and (state_id, seq) for events. The index applies Set or Remove only when that revision exceeds the stored summary revision, and Remove keeps a tombstone so a delayed older Set cannot resurrect the state; tombstones never appear in queries. An adapter that indexes asynchronously persists the publication intent in the same transaction as the commit, delivers it until applied, never exposes a summary for an uncommitted revision and converges on the latest one. States committed before an index existed are absent until their next commit with a summary; an adapter may rebuild its index offline from stored states.

query_states orders by (updated_at_ms, state_id) descending and query_events by (at_ms, state_id, seq) descending; their next cursor is passed back as after. read_events orders by seq in the requested EventOrder between exclusive after and before bounds; an ascending page's next is passed as after and a descending page's next as before. A page holds at most limit entries, and next is the cursor of its last entry and is Some only when more matching entries existed at query time. Pages are live keyset pages rather than snapshots. A zero limit, including the Default value of every query, returns an empty page without a cursor, and usize::MAX is a valid limit. Adapters impose no hidden caps; a backend with a protocol limit pages internally.

scope, parent and state_id match by exact equality, and every requested attribute pair must match exactly. kinds match any listed kind, and an empty list does not filter. text matches when any pattern is an ASCII-case-insensitive literal substring. StateQuery.text matches the union of a state's title, preview and event texts; callers that need prompt-only matching use query_events with a kinds filter. An event matches through its text, and events without text never match a text filter but still match by kind. query_events covers events of states with a live summary and its scope filter uses that summary's scope, so writers keep a state that has committed events summarized until the state is retracted; EventHit carries the state_id, and callers find the workspace and other fields from that state's summary. Ranked, tokenized or snippet search is not part of this contract; adapters may offer it separately.

A Durable Object adapter keeps one single-writer object per state. commit runs as one storage transaction that checks the fence and revision, inserts records, appends events from a stored seq counter, replaces the payload and records the publication intent, and acknowledges only after the write is durable. read_state, read_records and read_events are local reads on that object. Summaries and event texts are delivered to an index, such as D1 or a per-scope catalog object, idempotently by (state_id, revision) and (state_id, seq) with tombstones, and the index serves query_states and query_events.

StateStore::commit_many takes owned commits for distinct states and returns one result per commit in order, each with exactly the outcome commit would report for it alone. The default runs commit sequentially. Adapters may write the whole group with one synchronized write, but must judge every commit independently against its own fence and revision, acknowledge none before the shared write is durable, and never let one commit's rejection change another's outcome. A failed or interrupted group may leave any subset committed; every commit whose result is not success is uncertain unless it is NotCommitted, Fenced or Conflict.

StateStore::supports_events reports whether commit records events. It defaults to false, matching the default commit, stays fixed for an adapter, and adapters that record events return true. Wrappers forward it from the adapter they commit through.

This contract does not provide a mutable application-resume blob. Hosts that need one, for example a single replaced compressed row, keep it in their own StateStore adapter transaction; nanocode checkpoint records are immutable and content-addressed.

Payload records are addressed by BLAKE3, which is several times faster than software SHA-256 in WASM and uses WASM SIMD where the host build enables blake3's wasm32_simd feature. A payload under 16 KiB is one inline record keyed `b3:` plus the hash of its JSON. A larger payload is split into content-defined chunks keyed `c:` plus each chunk's hash, and its manifest record, `%` followed by the chunk hashes, is keyed by the hash of the manifest itself, so encoding hashes each byte once. Loading verifies the manifest and every chunk. Keys without the `b3:` prefix are SHA-256 records written by earlier builds: their inline records and `#` manifests load and verify with SHA-256, and `EncodedPayload::matches_key` treats a SHA-256 key of the same content as a match so receipts, steers and step inputs recorded before the change still compare equal.

A manifest that would reach 16 KiB becomes a tree instead of one growing record: leaf hashes are cut into groups where a hash prefix is divisible by CHUNK_AVG / 64, with CHUNK_MIN / 64 to CHUNK_MAX / 64 hashes per group, so a node stays the size of a data chunk. Each group is a content-addressed `c:` record and the payload key holds the root, prefixed `^` above the leaf level. A flat manifest grew by 64 bytes per chunk on every save, which made total manifest storage quadratic in session length; with the tree a save rewrites only the groups around its edits and the path to the root. On a local 60-turn Claude session with 60 KiB random-text replies (a 4 MB conversation), with A/B runs on an idle 24-core Linux host, manifest bytes fell from 2.39 MB to 1.55 MB and session storage from 38.0 to 36.4 MB, with WASM CPU per turn unchanged at about 80 ms; the saving grows with session length.

StateStore::peek is required: SessionStore::load, resume, branching, subagent parents and child journals read state through it without fencing, so an adapter without it fails only after sessions exist. StateStore::owner returns the current owner token of a state without fencing; its default reports the query as unsupported, which makes AgentRuntime treat a live agent's ownership as unknown. MemoryStore, KeyValueStore, JSONL, SQLite and Postgres implement it. StateStore::concurrent_handle defaults to None. An adapter returns an independent handle only when its operations stay correct while running concurrently with each other, including on the same state, because SharedStore then runs every operation on its own handle instead of queueing all states behind one another.

KeyValueStore implements StateStore over a host KeyValue with four operations: get returns a value and its version, put_values writes values unconditionally, compare_and_swap stores a version and value only when the current version equals the expected one or, with None, when the key is absent, and the optional list_keys returns the keys under a prefix for SessionStore::list. get_values defaults to sequential gets; hosts with batch reads or writes override get_values and put_values. Versions are chosen by the adapter as `fence.revision.owner`, so hosts store them verbatim and compare them, never generate them. compare_and_swap must be linearizable for one key; eventually consistent stores such as Cloudflare KV cannot back it. The head of a state is `{prefix}state/{state_id}` holding the payload; records are `{prefix}record/{state_id length}/{state_id}/{key}`, content-addressed, written before the head swap and never deleted, so a failed or uncertain replace can leave only unreferenced records. A record write failure is NotCommitted because the head was not swapped. A failed swap rereads the head to report Fenced or Conflict; a refused swap of the current version is a Backend error. Acquisition retries its swap until it installs the next fence, because each failure means another owner advanced the head. KeyValueStore clones share the host and report concurrent handles, so hosts must accept concurrent calls. A Durable Object host implements compare_and_swap in one synchronous storage transaction, SQL hosts with `UPDATE ... WHERE key = ? AND version = ?` or `INSERT ... ON CONFLICT DO NOTHING`, Redis with a script comparing a stored version field, DynamoDB with a condition on the version attribute, and object stores with the version in metadata and an ETag-conditional put.

StateStore::supports_summaries reports whether commit publishes summary updates. It defaults to false, stays fixed for an adapter, and wrappers forward it. Summary-capable adapters return true independently of event support; MemoryStore supports both. Drivers skip summary preparation and preview reads when this capability is false.
